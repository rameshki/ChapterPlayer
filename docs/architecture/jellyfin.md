- Jellyfin (J1 built on `stage-j/j1`, PR #86, Tasks 1 to 8 of `docs/superpowers/plans/2026-11-08-jellyfin-j1-j2.md`; add, sign in again, sync, browse and stream; J2 (Tasks 10 to 14, branch `stage-j/j2`) sends progress back, see the end of this paragraph; host-tested against synthetic fixtures only, not yet run against a real Jellyfin server): `ServerSource.JELLYFIN` (last; Room unchanged), book ids `jf_<item id>` (`domain/jellyfin/JellyfinBooks.kt`). Labels for a kind of server go through `serverKindName` (`domain/browse/ServerNames.kt`). Source badges show for any two kinds of server; the Jellyfin pill is "JF" (palette `jellyfinBadge` / `jellyfinBadgeBg`). Jellyfin covers are anonymous (`CoverAuth.NONE`, only under the server's own address). The token travels only in `Authorization: MediaBrowser ...` (`jellyfinAuthHeader`, `domain/jellyfin/JellyfinAuth.kt`; never in a URL, never `X-Emby-*`), with the DeviceId `chapterplayer-<install id>-<server row id>` (`jellyfinDeviceId`; `InstallId` = `PlexClientIdentifier`'s stored value). `data/remote/jellyfin`: `JellyfinApiService` (its `getPublicInfo` checks the status and decodes the text itself, so it also works on the probe client, which has no JSON converter), DTOs, `fetchAllAudiobooks` (pages of 200), `JellyfinSignIn` (public info on the probe client, version gate `checkJellyfinServer`, identity check against `ServerStatusRecord.jellyfinServerId` on Sign in again, then `AuthenticateByName` and the Books views; texts in `domain/jellyfin/JellyfinTexts.kt`); `JellyfinLibrarySource` (`data/source`, mapping in `domain/jellyfin/JellyfinMapping.kt`; per-view failures in `failedLibraries`; the last snapshot's user data, under 60 s old, answers `fetchAllProgress`; 401 blanks the token like Plex; the sync merges its progress like ABS, no bookmarks); setup in `ui/settings/JellyfinSetup.kt` (`JellyfinSetupHandler`, row id made before sign-in) and `JellyfinSignInSection.kt`; Servers page Test connection reads only the public info. The server id kept at the first sign-in is required: setup fails when it cannot be kept, Sign in again and an address change refuse without it, and a sync first checks the address's public info names it before any token goes out (calls outside a sync are not checked). Playback: `startPlayback` (one track, `domain/jellyfin/JellyfinPlayback.kt`: static stream address, mime table, new play session id) and an explicit Jellyfin arm in Android's `openAuthorized` and iOS's `StreamAuthorizer` (`jellyfinStreamHeader`; 401 blanks the token, 403 not allowed). Three kinds: tie order ABS, Jellyfin, Plex (`kindRank`); Jellyfin cannot download until J3 (`ServerSource.canDownload`, `SourceChoice.forDownload`, used by `chosenDownloadSource`, `downloadableMembers`, the Download from card, bulk Download and the menus); fixtures in `fixtures/jellyfin`. J2 (host-tested only, not yet run against a real server): rules in `domain/jellyfin/JellyfinProgress.kt` (`jellyfinLivePlan`, `jellyfinPushPlan`, `inThresholdBand`, `thresholdsOf`); the live session reports through `/Sessions/Playing` (first report of a load), `/Sessions/Playing/Progress` (`timeupdate`, or `pause` with IsPaused) and `/Sessions/Playing/Stopped` (always with PositionTicks; at the end itself when the close is within 1 s of the end), and where the server's audiobook thresholds would lose the place (the first `MinAudiobookResume` minutes or the last `MaxAudiobookResume`, read from `/System/Configuration` with each sync, unreadable keeps the last known else 5 / 5) and on every pause the exact `POST /UserItems/{Id}/UserData` write follows; an unknown session throws so the position is queued; a book set finished while loaded pins its session (sends nothing) until set not finished. Queued positions and mirrors go only through the UserData write (no session, no thresholds), dated with `pushProgress`'s new `playedAtMs` (the row's time; for a mirror the source copy's `lastPlayedAt` when older, `BookRepositoryImpl.playedAtOf`); finished is `POST /UserPlayedItems/{Id}`; Mark as not finished writes position 0 with `Played = false` (`DELETE /UserPlayedItems` stays in the service for the server check). Jellyfin is a mark target (`MARK_TARGETS`) and `ServerProgressRefresher` refreshes ABS and Jellyfin (not Plex). Rows J1 queued (refused as "not yet") are delivered by the flusher as UserData writes, or dropped when the server holds newer listening or after 30 days. Diagnostics shows the copy's user data (`JellyfinReading` on `ServerProgressReading`); `redact()` removes a `MediaBrowser ...` header value
- Downloads (J3): `JellyfinDownloadSource` is on (`canDownload()` true) and was run for real on 19 Nov against a real Jellyfin 12.4 server on an Android 15 emulator with a throwaway user: sign in through Add Server, a download of the smallest book (5,552,556 bytes, exactly the size the server reported, one `.m4a` named by the item id, plus its cover), offline playback from the file with the network down, and the place (30.007 s) reaching the server after the network came back. Recorded answers: `fixtures/jellyfin/recorded`, `tools/jellyfin-record`. Quick Connect is not built. Plan: `docs/superpowers/plans/2026-11-19-jellyfin-j3.md`.
- Seen on a real Jellyfin 12.4 server (19 Nov, a throwaway user, `tools/jellyfin-record --with-writes`), which the progress code assumed from the API description: a play session stopped at 90 s of a 23.6 h book leaves `PlaybackPositionTicks` at 0 with `PlayCount` 1 (the 5-minute audiobook threshold drops short places, which is why the app writes the exact place itself); `POST /UserItems/{id}/UserData` with 30 s and `Played = false` keeps exactly 30 s (no thresholds); `POST /UserPlayedItems/{id}` gives `Played = true`, position 0, `PlayCount` 1; `DELETE /UserPlayedItems/{id}` gives `Played = false`, `PlayCount` 0, position 0. The session reports answer 204 and the played-flag calls 200 with the user data. Not seen: the same calls on a book already in progress, or the 403 of an account without the Download permission.
- Quick Connect (J3 task 4, spec 5.1; built and run for real on 19 Nov): `domain/jellyfin/QuickConnect.kt` holds the pure rules (read every 5 s, give up after 5 minutes, an unknown request ends the wait at once, a failed read is tried again and says so) and the words. `JellyfinSignInPort` has three steps next to `withPassword`: `startQuickConnect` (the same address checks as a password sign-in, then `GET /QuickConnect/Enabled`, then `POST /QuickConnect/Initiate`), `pollQuickConnect` (`GET /QuickConnect/Connect?secret=`) and `finishQuickConnect` (`POST /Users/AuthenticateWithQuickConnect`, then the same finish as the password: identity check, the user's views, the books libraries; `JellyfinSignIn` shares that finish). `JellyfinSetupHandler` runs one wait at a time (it counts ticks, so a slow read does not shorten the wait), in Add Server and in Sign in again (which keeps the stored-server-id check); Cancel, Back and leaving the screen stop the polling and forget the secret, with no call to the server. The secret is in memory only: `QuickConnectRequest`, `JellyfinQuickConnectResultDto` and `QuickConnectUi` leave it (and the code) out of `toString`, and the debug HTTP logger masks any `secret=` in a request line (`maskQuerySecrets`). Deviation from the spec: the button is not hidden when Quick Connect is off (that would need a read while the address is typed); it is shown once an address is typed, and a server that has it off says so when the button is tapped. Seen on a real Jellyfin 12.4: a 6-digit code, the sign-in worked after an approval through `POST /QuickConnect/Authorize?code=` as another signed-in user, and the log showed only `secret=[removed]`.
- Quick Connect, after the independent review (19 Nov): Save stores the token under the address the sign-in was made to (`resultAddress`), never the field's text by then, and the address field is disabled while a sign-in runs (a token for one server must not be saved for another; the password path had the same hole with a window of a second, Quick Connect would have had five minutes). Every call of the wait has its own limit (`QUICK_CONNECT_READ_TIMEOUT_MS` 5 s, start 45 s, final sign-in 30 s): a read that hangs is a failed read and its limit counts as time waited, so a host that goes dark ends the wait at about five minutes, not half an hour. Cancel works whenever the wait runs (before the first code, and while the approved sign-in is being finished); a cancelled run cannot clear the next run's state. A server error on `/QuickConnect/Enabled` is a server error, not "off". Known and accepted: whoever approves the code becomes the signed-in user on that row (Sign in again does not check it is the same user; the password path allows the same by typing another name; the stored server id is checked). Leaving the screen ends the wait through the ViewModel scope (not a `DisposableEffect`, which would also cancel it on rotation).
