# Downloads

The downloader, its sources, the UI and the platform parts.

Detail moved out of `CLAUDE.md` (review R8); keep it current when this area changes.

- Downloads (Stage 3; Plex since Stage 4; common since Stage 5 step 5): `DownloadController` (commonMain; `DefaultDownloadController` over a `DownloadScheduler`: WorkManager on Android, `IosDownloadScheduler` on iOS) queues, pauses, resumes and removes books; status and bytes live in `downloads` / `download_files` (Room v6; v7 adds each file's length and type) and only change from the expected status (`updateStatusIf`), so a pause or removal is never overwritten. `DownloadWorker` (a dataSync foreground job, unique name `download-<bookId>`, network constraint from `AppSettings.downloadWifiOnly`) runs `BookDownloader` (`data/downloads`): it asks the server kind's `DownloadSource` (`AbsDownloadSource`, `PlexDownloadSource`; Koin binds both) for the files and chapters, checks the space, and fetches file after file with `FileDownloader` (one ranged GET per file into `<ino>.<ext>.part`, renamed when complete; its own Ktor client with no request timeout, a stall check before and after the headers, the source adds the credential per request (ABS refresh once on 401), no redirect to another host, disk errors fail instead of retrying; a request that cannot connect asks the source for a new address (`afterConnectionFailure`, Plex: `PlexConnectionManager.afterFailure`) and resumes the same `.part` there with Range). Audiobookshelf: files from `GET /api/items/{id}` audioFiles, `/api/items/{id}/file/{ino}/download` with the bearer. Plex: one file per album track (`plexDownloadPlan`, `domain/plex/PlexDownloads.kt`; the `ino` column holds the track's rating key, the extension comes from the part path's file name, else its container; a book with a track of unknown length is refused at plan time with the streaming text, since it could never play; a size Plex leaves out is read from a `Range: bytes=0-0` request (`plexSizeAnswer`: a 2xx without a size fails the book with "Plex did not report the file size", a 404 as audio missing, anything else is tried again later)), each part fetched under the server's address in use (read from the server row per request) with `X-Plex-Token`; a 401 blanks the token (`PlexLibrarySource.signedIn`). Before any Plex download request with the token (plan, size request, files, cover, lengths) `PlexDownloadSource` runs `PlexConnectionManager.forTokenRequest` (`beforeSync`, then null for a plain http address still not verified on this network: nothing is sent and the job tries later), and a plan that cannot connect asks `afterFailure` for a new address and is tried there once. `DownloadLengthFiller` asks the source too (Plex: the track lengths; a Plex book whose server answered without the missing lengths is not asked again until the sync rewrites its row, `cachedAt`). The downloader core (`FileDownloader`, `BookDownloader`, both sources, `DefaultDownloadController`, `DownloadLengthFiller`, `DownloadQueueRestorer`, `DownloadLocation`, `bookDirectory`) is in commonMain and reaches the disk only through the `DownloadFiles` port (`data/downloads/DownloadFiles.kt`: length, truncate-and-append sink, fsync, atomic rename, delete, listing, free space, path joins; paths are strings as stored in `download_files.path`): `AndroidDownloadFiles` (java.io/nio, what the downloader always did; folder work on `Dispatchers.IO` passed in by Koin) and `IosDownloadFiles`. One job per book and one book at a time; `DownloadJobs.whileIdle` is how deletes wait for a stopping job. New downloads go to `<root>/downloads/<serverId>/<bookId>/`, the root being the Settings choice (`SettingsDownloadLocation`: internal storage or the app folder on a mounted external volume / SD card, falling back to internal); a planned download stays in the folder its `download_files` paths name, and removal deletes the folders those paths point to, so changing the location affects new downloads only. The pure rules are in `domain/downloads`
- Downloads UI: `DownloadOverview` (`data/downloads`, `RoomDownloadOverview`) is what screens read: one `DownloadRow` per book, fraction and bytes from the file rows, speed and time left live from `BookDownloader` (`LiveDownloadProgress`), plus storage used. Book details (`DetailsDownload.kt`, `DownloadControl.kt`) shows Download (with the size from the server), progress, Pause / Resume / Cancel, Try again, and Remove download with a confirmation, for Audiobookshelf and Plex books; the start is disabled offline. A merged book's control shows whichever copy has a download, else this page's copy; Every copy of a merged book that has a download row gets its own control (`otherCopyDownloads`, each labelled with type and server; Pause / Resume / Cancel / Try again / Remove act on that copy only; this page's copy is the main control). Download picks the copy by `chosenDownloadSource` (the "Download from" choice) or opens the "Download from" sheet, whose rows show each copy's real download state from the rows (`RoomDownloadStates` reads every unfinished status as DOWNLOADING, so the sheet does not rely on it): Downloaded, Queued and Downloading cannot be chosen, Paused and Failed can (choosing resumes that download), a copy with no download can ("Download this copy too" when another is on the phone), each only when its server answers, with its size once the server says. "Download another copy" shows while some copy has a download and a copy with none has a server that answers. The first download asks for notifications once through `NotificationPermission` (`AndroidNotificationPermission`, lent the launcher by `MainActivity`); the download runs either way. The Downloads tab (`ui/downloads`) lists every download (active first, then title) with row buttons, a source badge (`SourceBadge`, shown when servers of both kinds are added) and a used / free header. Settings, Downloads: Wi-Fi only (a change reschedules waiting and running jobs, `DownloadController.reapplyWifiSetting`), location, and storage limit (`AppSettings.downloadStorageLimitBytes`, read by the downloader's space check). "Remove finished downloads" (branch `stage-4/multi-select`, host-tested only; `RemoveFinishedDownloadsCard` + `FinishedDownloadsViewModel` on the Downloads tab and in Settings, Downloads and offline): `finishedDownloadsToRemove` (`domain/downloads/FinishedDownloads.kt`) picks every DONE download of an entry whose progress is finished (mirrored included), never an entry holding the loaded copy or the entry Up next will start (`planUpNext` with `upNextCanPlay`, the loaded book counting as ending); the view model runs only while shown (`WhileSubscribed`) and drops an open question when nothing qualifies; the card is hidden when none qualifies, asks "Remove 7 downloads and free 3.4 GB?", then `DownloadController.remove` one after another and one snackbar
- Android 15 dataSync time limit (R5, targetSdk 36): WorkManager's `SystemForegroundService` gets `onTimeout` after 6 hours of dataSync foreground time in 24 and stops the download job with `STOP_REASON_FOREGROUND_SERVICE_TIMEOUT` (WorkManager 2.12; read only on API 31+). The downloader saves the bytes and puts the book back to QUEUED as on any stop; `DownloadWorker` then calls `DownloadTimeLimitHold.afterStop` (androidMain), which asks `DefaultDownloadController.afterStop(bookId, timedOut, appVisible)`: the pure rule `afterJobStop` (`domain/downloads/DownloadTimeLimit.kt`) gives NOTHING (not the time limit, or nothing waiting), CONTINUE_NOW (the app is in front, which gives Android's budget back: the stopped book is scheduled again at once) or HOLD_UNTIL_APP_OPENS (every QUEUED / DOWNLOADING download is replaced by a job delayed `TIME_LIMIT_HOLD_MS` = 24 h through `DownloadScheduler.scheduleLater`, so nothing tries a foreground start that would be refused; iOS's default schedules at once). On a hold the time is kept in the `downloads` SharedPreferences (`time_limit_held_at`, the process may die before the app opens) and a "Downloads paused" notification (`timeLimitNotice`, channel `download_notices`, no title or server named) opens the app; `MainActivity.onStart` calls `onAppVisible`, which releases the hold (`releaseTimeLimitHold`: every waiting download scheduled again at once, replacing the delayed job) and removes the notice. Statuses are never changed by the follow-up (no schema change). A `setForeground` the system refuses (`ForegroundServiceStartNotAllowedException`, also caught inside WorkManager's service) still carries on as ordinary background work with the bytes kept. Host-tested (`DownloadTimeLimitTest`, `DefaultDownloadControllerTest`, `DownloadRaceTest`: a stopped job keeps its 700 bytes, is held, and continues with `Range: bytes=700-` once released); not yet seen on an Android 15 or 16 device
